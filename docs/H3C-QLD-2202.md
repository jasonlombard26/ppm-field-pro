## Implemented behavior

- Both `index.html` and `pc.html` load `asset-features-v39.js` after existing feature/photo/backup modules. Desktop photo suppression is removed.
- Inputs have separate optional text `moduleType`, `moduleNumber`, and `contactIdReportingCode` fields. Values such as `001` and `A/02` remain strings. Legacy `module`, `pointId`, unknown properties and existing reporting identifiers are retained. No hardware enumeration, assumed address semantics, Contact ID length constraint or inferred reporting code is introduced.
- Add/edit inputs and the existing CSV/Excel row mapper understand exact named columns for the three fields. Generic input imports remain the existing append workflow; they are **not** the proposed reviewed customer-report importer. Complete JSON/recovery exports and revision-controlled site payloads preserve the new asset fields.
- A head-end system is one existing `db.assets` record, with `headEnd: true`, `platform`, `appliesTo`, and optional `headEndType`. New records also use `recordType: headEnd`. Applicability can include Access Control, Intrusion, both, or neither (for other head-end equipment). Multiple systems remain separate, even with identical names.
- `headEndId` associates an input/device/asset with one actual system. An explicit **Use Existing Asset** flow retains that asset's ID and all unedited fields. It does not merge, delete or deduplicate records. Potential duplicates require operator review; automatic name matching is intentionally absent. Unresolved legacy references remain selectable and use Generic labels.
- Head-end photos use the same asset reference from both sections. Adoption freezes the photo section without moving objects. Backups retain their original `sites/<site-id>/head-end/backups/<filename>` paths. Optional `headEndBackupLinks` rows (`siteId`, `assetRef`, `cloudPath`) associate an existing file once with a system. The site-wide backup list still exposes unassigned legacy files. Assignment does not copy or rename files. Technicians can assign/upload; backup deletion remains admin-only.
- Generic, Integriti and Gallagher labels are centralized. Integriti inputs display **Zone Input** and **Area**; Gallagher uses **Input** and **Alarm Zone**; Generic uses **Input** and **Intrusion Area**. Labels target only the intrusion/input fields. Changing a profile does not rewrite values, hardware models, IDs, access groups, controller types or stored results. Reader/controller/door/module fields are not blindly relabelled as vendor-specific hardware.
- Photos retain `db.photos`, `siteId`, `assetRef` and existing cloud paths. Multiple attachments are supported. New files are durably queued locally before upload, with UUID paths and no overwrite. Allowed types match the existing bucket: JPEG, PNG, WebP, GIF, HEIC, HEIF. New local-first captures have a **2 MiB per-file** limit and **3 MiB encoded pending-queue** ceiling; actual browser quota may be lower. These are stricter client cache protections than the unchanged 20 MiB bucket limit. Large phone photos currently need resizing before selection.
- Queued photos retry on an available immediate connection, the browser online event, or **Refresh / upload pending photos**. Failed uploads remain pending. A duplicate UUID path after interrupted acknowledgement is accepted only after verifying the existing object name and size. Account-generation checks prevent late reads/uploads from modifying a switched account. Pending photos remain in account recovery exports, not site JSON.
- Storage discovery supports new categories and historical access-control fallback paths. Cloud photo bytes remain outside site JSON/CAS payloads, following the existing architecture. Photo add/remove/rename and new record edits consult the same in-memory account/role/cache state as sync; RLS remains the server authority. Quota failures in new atomic record saves retain the previous visible state.
